\section{Introduction}
PLATE RECognition In PYthon (\texttt{platerecipy}) is a package tailored for 
plate identification on 3D spherical surface of mantle convection models and 
geodetic datasets\footnote{Though most \texttt{platerecipy} modules support a 
2D input, additional work remains for a full integration of such functionalities.}. 
At its core, \texttt{platerecipy}
uses Random Walker (RW) algorithm developed by \textcite{grady2006} but modified 
for a spherical surface. \textbf{The probability array obtained from RW is the 
main feature of this package that enables further quantitative analysis of the 
identified plates.}

\section{Dependencies}
Currently, \hl{Linux is the only supported platform}. Since MacOS is Unix-based, 
\texttt{platerecipy} is expected to be installed and used without a problem.
The main reason that Windows is not supported at this point is that there
some functionalities are implemented in \texttt{C} and require a slightly 
different compilation and linking procedure. Until the first release, 
availability of \texttt{platerecipy} on Windows is not a development priority.  

Concerning the \texttt{Python} dependencies, \hl{\texttt{pip} should 
automatically install the necessary packages}. Nonetheless, the following
includes the necessary dependencies:
\begin{itemize}
    \item \texttt{numpy} \parencite{numpy}: for array operations
    \item \texttt{scipy} \parencite{scipy}: for specific scientific utilities
    \item \texttt{matplotlib} \parencite{matplotlib}: for basic plots
    \item \texttt{pyvista} \parencite{pyvista}: for \texttt{vtk} output and 3D visualization
    \item \texttt{pandas} \parencite{pandas}: for additional io operations
\end{itemize}


\section{Installation}
Until the packages is released on PyPI, \texttt{platerecipy} can be installed using 
\texttt{pip} on the shell as follows:
\begin{lstlisting}[language=bash]
cd dist/
python -m pip install platerecipy-?.?.?.tar.gz
\end{lstlisting}
where \texttt{platerecipy-?.?.?.tar.gz} is the installation tar file for the desired 
version. Note that all \hl{installation tar files can be found in \texttt{dist} 
subdirectory.}

\section{Basic interface}
For most purposes, only the following modules are of interest:
\begin{itemize}
	\item \texttt{grid}: providing class and function definitions to interpolate and construct a grid,
	\item \texttt{model}: providing class and function definitions to defined a plate model and identify candidate plates, andthese
	\item \texttt{io}: providing helper functions for outputting in various formats.
\end{itemize}
Accessing these modules are done simply using \texttt{import}:
\begin{lstlisting}[language=Python]
from platerecipy.grid import SphericalGrid

from platerecipy.model import PlateModel

from platerecipy.io import save_as_mat, save_as_vtp, save_as_csv
\end{lstlisting}
(though discouraged, one can import all the content by \texttt{*} wildcard).

\texttt{platerecipy} is developed under the notion that it must accommodate users 
with different dataset formats and from different grid structures (e.g., spherical, 
YinYang, icosahedral, etc.). Accordingly, as much as possible, the interface
must refrain from assuming any format or structure specific layout to the input 
arguments. Consequently, the trade-off of optimizing for minimal conversion burden 
on the end user is more processing and higher memory usage. However, this extra 
cost at the post processing is vanishingly small compared to the original cost of 
running numerical models. 

With the aforementioned principle in mind, all that is expected from the user 
is to have access to, at least, the following arrays:
\begin{itemize}
    \item the Cartesian $x$, $y$, and $z$ coordinates (will refer to it as \texttt{input\_xs}, \texttt{input\_ys}, and \texttt{input\_zs}),
    \item as well as the corresponding field values (will refer to it as \texttt{input\_field}).
\end{itemize}
Furthermore, though \hl{all input arrays are assumed to be \texttt{numpy}} \parencite{numpy} arrays,
they can have any shape (flat or multidimensional).

The fist step is to generate a grid:
\begin{lstlisting}[language=Python]
from platerecipy.grid import SphericalGrid

# generating a consistent grid for interpolation
grid = SphericalGrid(input_xs, input_ys, input_zs)
\end{lstlisting}
The \texttt{SphericalGrid} object is itself a derived type of a generic class 
\texttt{Grid}, but it informs the code whether additional considerations (e.g., 
applying the wraparound boundary condition or spherical distances) are required.
Then, our \texttt{SphericalGrid} object is to be used to interpolate \texttt{input\_field}
to the input points to a spherical grid. \hl{Segmentation is performed on the linearly-interpolated uniform spherical grid.} Interpolation process is 
performed using the method \texttt{interpolate\_field}:
\begin{lstlisting}[language=Python]
# interpolating an input field
field = grid.interpolate_field(input_field)
\end{lstlisting}
It should be noted that for input fields such as viscosity or strain-rate
(which vary by orders of magnitude), the optional argument \texttt{take\_log}
should be set to \texttt{True} in order to the linear interpolation is performed in the log space (and then converted back).

With the \texttt{grid} object and the interpolated field \texttt{field}, we have the necessary arguments to perform plate detection. To initiate the process, a \texttt{PlateModel} object is to be constructed as follows:
\begin{lstlisting}[language=Python]
from platerecipy.model import PlateModel

# initializing a plate model
m = PlateModel(grid)
\end{lstlisting}
The newly-created object \texttt{m} carries (a pointer) to the \texttt{grid} object which includes information about the original input as well as the 
interpolated grid structure. Though it would have been possible to keep
interpolation under the hood (given \texttt{PlateModel} carries a \texttt{Grid} attribute), the user may want to further manipulate the 
interpolated field before passing it for plate detection. That is why
the two steps are kept separate. The importance of the class \texttt{PlateModel}
is in the fundamental idea that what defines plate interior/boundary must be 
made explicit and consistent across subsequent snapshots of the same model. The 
\texttt{PlateModel} class has the ability to stack several fields with different
corresponding weights and normalize the stacked field to span $[0, 1]$. Stacking 
fields are done through the \texttt{PlateModel.stack\_field()} method as follows:
\begin{lstlisting}[language=Python]
# stacking the interpolated field
m.stack_field(field)
\end{lstlisting}
Once again, for fields that vary by orders of magnitude, \texttt{PlateModel.stack\_field()}
accepts an optional argument \texttt{take\_log} which if set to \texttt{True} it takes
the logarithm to flatten the distribution. Most importantly, \hl{the stacked fields 
are assumed to be markers of deformation such that 0 and 1 correspond to minimal 
and maximal deformation.} For a field that is opposite of this (i.e., its high corresponds
to low deformation and vice versa), there is an additional argument \texttt{invert} 
which ensures the stacked field stays consistent.

Once all the fields (if multiple) are stacked, the \texttt{PlateModel.find\_plates()}
method performs segmentation:
\begin{lstlisting}[language=Python]
# finding plates on the stacked field
plate_IDs = m.find_plates(
    boundary_quantile  = 0.9,          # threshold for the boundaries 
    # ...
)
\end{lstlisting}
The \texttt{PlateModel.find\_plates()} method both returns the segmentation result, 
and also it save them in the model object as \texttt{m.plate\_IDs} (containing segmentation IDs) 
and \texttt{m.ID\_probs} (containing the associated probabilities).

\subsection{Overall structure}
The source code is effectively divided to two portions:
\begin{itemize}
    \item \texttt{src/platerecipy}: where the \texttt{Python} modules reside, and
    \item \texttt{src/clib}: where various backend utilities are implemented in 
    \texttt{C} for better performance.
\end{itemize}

\subsection{\texttt{segmentation} module}
In \texttt{platerecipy}, Random Walker (RW) segmentation algorithm \parencite{grady2006}
is implemented primarily for the surface of a sphere (i.e., 3D spherical shell), 
though it is capable of performing segmentation on a flat 2D plane, as well.
In short, linear system construction (i.e., vertex/edge associations, label ordering, etc.)
is performed using the functions implemented in \texttt{C} (i.e., \texttt{segmentation.h}),
while the numerical solution and the interface is done through the \texttt{Python}
side (i.e., \texttt{segmentation.py}) using \texttt{NumPy} \parencite{numpy} and \texttt{SciPy}
\parencite{scipy} routines.

The user interface is implemented by the function:
\begin{lstlisting}[language=Python]
def random_walker(
    data                            : np.ndarray, 
    labels                          : np.ndarray,
    beta                            = 100.,
    is_spherical                    = False, 
    max_beta_reduction_attempts     = 3,
    beta_reduction_fraction         = 0.9,
    beta_reduction_residual_tol     = 1e-3
)
\end{lstlisting}
and returns the plate IDs and the ID probabilities as a tuple \texttt{(IDs, probs)}.
Yet, function \texttt{random\_walker} is effectively a wrapper that prepares the input
to and output from functions \texttt{get\_AB} and \texttt{solve\_AX\_B}. The \texttt{data}
array is the input field/image and is assumed to be floating point. The \texttt{labels} 
must be of the same shape as \texttt{data} but an integer field with the unmarked 
regions labeled with zeros and each marked patch with a distinct but sequential 
positive integer label. Since overly large values for $\beta$ destabilize the linear 
system, \texttt{random\_walker} has a built-in mechanism that gradually reduces input \texttt{beta}
by a factor of \texttt{beta\_reduction\_fraction}, \texttt{max\_beta\_reduction\_attempts}
many times until the $L_2$ norm of the residual of the solution to the numerical 
system is driven down below \texttt{beta\_reduction\_residual\_tol}.

Function \texttt{get\_AB} constructs the linear system and returns:
\begin{itemize}
    \item \texttt{A}: the sparse $L_{\mathrm{unmarked}}$ matrix,
    \item \texttt{RHS}: the full right-hand-side matrix $-B^T \left [m^{(1)} m^{(2)} \cdots m^{(N)} \right ]$, and
    \item \texttt{org2org}: the vector that maps the ordered node indices to the original indexing 
    where \texttt{ord2org[i\_ord] == i\_org}.
\end{itemize}
whose values are subsequently passed onto \texttt{solve\_AX\_B} which accepts:
\begin{itemize}
    \item \texttt{A}: the left-hand-side matrix,
    \item \texttt{B}: the right-hand-side matrix (essentially, \texttt{RHS} from \texttt{get\_AB} and not to be confused with $B$ in \cite{grady2006}) and must at least have two columns (otherwise its a trivial or an untenable solution), 
    \item (optional) \texttt{solver}: by default set to LU decomposition (\texttt{'LU'}) but other options (e.g., \texttt{'direct', 'CG', 'FA'}) are available, and
    \item (optional) \texttt{safe\_mode}: by default set to \texttt{True} which solves for all the probabilities (as opposed to solving for $N-1$ probabilities and assuming $p_N = 1 - \sum^{N-1} p_i$).
\end{itemize}
Finally, the solution to the linear system (which is ordered) is converted back to 
the original indexing using \texttt{ord2org}.

\subsubsection{RW on a sphere}
This mode is enabled by passing \texttt{is\_spherical=True} and suggests that 
the input grid is a uniform spherical grid with wraparound boundary conditions.
Since it is assumed that the \texttt{data} is an array containing the mercator 
projection of a sphere, to be consistent with the rest of the package, it is also 
assumed here that:
\begin{itemize}
    \item \texttt{data[:, 0] == data[:, -1]} to satisfy wraparound boundary conditions (and similarly \texttt{labels} and the downstream output),
    \item \texttt{data[0, :]} are all the same and correspond to the north pole at $\theta = 0$, and
    \item \texttt{data[-1, :]} are all the same and correspond to the south pole at $\theta = \pi$.
\end{itemize}
Accordingly, at the entry point in \texttt{random\_walker}, both \texttt{data} and 
\texttt{labels} are trimmed off of their redundant last columns, and all the 
helper \texttt{C} functions in \texttt{segmentation.h} that end with \texttt{\_sph}
assume the input arrays do not have the redundant column. This is critical as 
the arrays are passed by providing the pointer to the first index and the number of 
columns plays a fundamental role in the functions' ability to access, map, and order 
the indices. Furthermore, the last node on the first row and 
the first node on the last row of the trimmed array are considered as the north 
and south poles, respectively (see Figure \ref{fig:sph-grid}).
